## D-001. src-layout вместо плоского пакета — принято

**Контекст.** Требование курса — установка через pip. Частая ошибка: тесты
проходят локально, потому что импортируют пакет из рабочей директории,
а собранный wheel сломан (забыт файл, `py.typed` не попал в сборку).

**Решение.** Пакет лежит в `src/ranklens/`. Тесты импортируют только
установленную версию. В CI отдельная задача собирает wheel, ставит его
в чистый venv и запускает `ranklens --version` вне репозитория.

**Альтернативы.** Плоский `ranklens/` в корне — проще, но скрывает ошибки упаковки.

## D-002. Poetry, lock-файл, версия в pyproject — принято

**Контекст.** Без lock-файла CI ставит последние версии ruff/mypy/pytest,
и их новый релиз может сломать CI без изменений в коде.

**Решение.** Управление зависимостями и сборка — Poetry 2.4 (бэкенд `poetry-core`).
Метаданные — в стандартной таблице `[project]` (PEP 621), dev-инструменты —
в `[dependency-groups]` (PEP 735), `poetry.lock` коммитится.
Версия — только в `pyproject.toml`; `__version__` читается через
`importlib.metadata.version("ranklens")`.

Проверено: для numpy Poetry сам разводит версии по маркерам Python
(на 3.14 — более свежая ветка), так что один lock не прижимает все Python
к самой старой совместимой версии.

**Альтернативы.** hatchling + pip — было в первой версии, без lock-файла.
uv — быстрее, тоже с lock-файлом; выбран Poetry, потому что с ним есть
опыт работы.

## D-003. Python >= 3.11, CI на 3.11–3.14 — принято

**Контекст.** Свежие numpy уже требуют 3.12, pandas 3 — 3.11.

**Решение.** Нижняя граница 3.11. Разработка ведётся на 3.11,
CI проверяет 3.11–3.14 × Linux/macOS/Windows. Нижние версии numpy/pandas
в `dependencies` — те, с которыми реально проходят тесты.

## D-004. Позиции с нуля, ранги с единицы — принято

**Решение.** В структурах данных — `position` с нуля (индекс в кортеже).
В формулах — `rank = position + 1`. Имена переменных различают эти понятия.

**Почему.** Формулы метрик (log₂(rank + 1), 1/rank) и propensity (1/rank)^η
записаны для рангов с единицы; ошибка на единицу в дисконте — самый частый
тихий баг в метриках ранжирования.

## D-007. `RankedList.docs` — tuple, а не list — принято

**Контекст.** Первоначальный дизайн: `RankedList` — `frozen` dataclass с полем `docs: list[DocId]`.
`frozen=True` запрещает переприсваивание атрибута, но не мутацию списка:
`ranked.docs.append(...)` сработает. Кроме того, dataclass со списком
нехешируем, хотя `frozen` обещает обратное.

**Решение.** `docs: tuple[DocId, ...]`, `scores: tuple[float, ...] | None`.
Список остаётся там, где нужна мутация: буфер накопления строк текущего запроса
в `iter_run` — сначала `list.append`, при смене query_id — `tuple(buffer)`.
Это и есть обоснование `list` для чеклиста: изменяемая структура для построения,
неизменяемая — для результата.

**Проверки в `__post_init__`.** `docs` и `scores` — именно `tuple` (mypy не защищает
вызывающий код без типизации, `TypeError`); длина `scores` совпадает с `docs`
(`ValueError`, ошибка программиста); документы в выдаче уникальны —
иначе `DuplicateDocumentError`, это ошибка данных (проверка через `set`, O(n)).

## D-008. Исключения: аргументы в `args`, текст в `__str__` — принято

**Контекст.** Исключение со своим `__init__(self, line_no, raw, reason)`
по умолчанию не переживает `pickle`: распаковка вызывает `cls(*self.args)`,
а в `args` лежит одна готовая строка.

**Решение.** Конструктор передаёт исходные аргументы в `super().__init__`,
хранит их в атрибутах, текст собирается в `__str__`. Тест проверяет
`pickle`-round-trip для каждого класса иерархии.

## D-009. Архитектурные границы проверяются тестом — принято

**Решение.** `tests/test_architecture.py` разбирает AST всех модулей пакета
и сверяет импорты с таблицей из CONTRIBUTING (раздел 4). Учитываются и импорты
внутри функций. Правило из документа, которое не проверяется, со временем

## D-010. `RankedList` — frozen dataclass, а не обычный класс — принято

**Вопрос из ревью PR #2.** Нужна ли неизменяемость и нужен ли dataclass.

**Dataclass против обычного класса.** Поведение нужно одно и то же: конструктор,
`__repr__` для отладки и сообщений pytest, `__eq__` по значению для тестов.
В обычном классе всё это пишется руками — больше кода без выигрыша.
`NamedTuple` тоже неизменяем, но сам является кортежем: `len(ranked)` вернул бы
число полей, объект можно распаковать и индексировать по полям — это ложный интерфейс.

**Нужна ли неизменяемость.** Ни одному алгоритму она не нужна. Её смысл —
гарантия: один `RankedList` читают несколько метрик подряд, он лежит в буферах
`PairedRuns` и может попасть в кэш; ни один потребитель не может испортить его
для остальных. Поля и так кортежи, поэтому гарантия почти бесплатна.
Хешируемость — побочный эффект, а не цель.

**Цена (замер, Python 3.11, 20 документов):**

| Вариант | нс на объект |
|---|---|
| dataclass(slots) / обычный класс со `__slots__` | ~110 |
| NamedTuple | ~170 |
| dataclass(frozen, slots) | ~350 |
| `RankedList` (frozen + проверки `__post_init__`) | ~1100 |
| для сравнения: разбить 20 строк TSV одного запроса | ~1900 |

`frozen` добавляет ~240 нс на запрос, основная цена — проверки (уникальность
документов). На миллион запросов это ~1 с при чтении, которое и так
в несколько раз дороже. Проверки остаются в типе: это единственное место,
через которое проходят все выдачи.

**Пересмотреть**, если профилирование `iter_run` покажет, что создание объектов —
узкое место: тогда проверки переезжают в reader, а тип становится `slots` без `frozen`.

## D-011. Идентификаторы — строки, а не `Hashable` — принято

**Вопрос из ревью PR #2.** Почему `str`, если идентификатором может быть `int`.

**Решение.** `QueryId`/`DocId` — `NewType` над `str`; целые идентификаторы
поддерживаются, но при чтении приводятся к строке.

**Почему.**

- Тихий баг: pandas прочитает qrels с id `int64`, а выдачу — с `str`;
  `qrels[1]` и `qrels["1"]` — разные ключи, метрика молча станет 0.
  Одна форма на границе `io` убирает этот класс ошибок целиком.
- Ведущие нули: `"007"` и `7` — разные документы, `int` их склеит.
- Порядок: merge-join в `PairedRuns` требует полного порядка, а `int` и `str`
  между собой не сравниваются. Контракт сортировки — строковый (Q-1).
- `Hashable` ничего не обещает, кроме хеша: ни порядка, ни сериализации в JSON-отчёт.

**Альтернативы.** `int | str` — те же проблемы смешения типов; обобщённые
(generic) типы по id — сложность без пользы для пользователя CLI.

## D-012. Входные форматы и разбор строк — принято

**Решение.**

- Форматы: csv, tsv, jsonl и **TREC** (сверх плана). TREC — стандарт обмена
  прогонами в IR, без него golden-тесты против `pytrec_eval` (неделя 6) требуют
  конвертации. Формат — по расширению (`.csv`, `.tsv`, `.jsonl`/`.ndjson`,
  `.trec`/`.run`/`.qrels`); `.gz`, `.bz2`, `.xz` распаковываются прозрачно
  (стандартная библиотека, без зависимостей).
- Два слоя: `formats` превращает файл в `Record` со строковыми полями и ничего
  не знает о прогонах; `schema` знает имена колонок и типы. Новый формат не трогает
  разбор, новая колонка не трогает форматы.
- Ошибки строки не бросаются из `formats`, а передаются в `on_error`: политику
  (strict — бросить, non-strict — посчитать и пропустить) задаёт reader в одном месте.
- **Всегда фатальны**, даже в non-strict: нет обязательной колонки в заголовке,
  неизвестный формат. Пропускать нечего — сломан весь файл.
- jsonl: числа приводятся к строке (D-011), `true`/`null`/объекты в обязательных
  полях — ошибка строки; в необязательных — игнорируются.
- Идентификаторы и сегменты обрезаются по пробелам; пустой id — ошибка строки.
  Числа: `score` и `relevance` — конечные float (`nan`/`inf` — ошибка),
  `rank` — int. Отрицательная релевантность допустима (в TREC бывает −1, −2).
- `Record`, `RunRow`, `QrelsRow` — обычные `slots`-dataclass без `frozen`:
  живут одну итерацию и никуда не передаются (D-010, условие пересмотра).

**Альтернативы.** `csv.DictReader` — сам не сообщает о лишних/недостающих значениях
(кладёт их в `None`-ключ), поэтому `csv.reader` и сравнение длины с заголовком.
pandas — не потоковый и тащит зависимость в `io` (CONTRIBUTING, раздел 4).

## D-013. Контракт порядка входа: grouped по умолчанию, sorted по запросу — принято (закрывает Q-1)

**Контекст.** Для потокового чтения одного прогона достаточно, чтобы строки
запроса шли подряд. Merge-join двух прогонов (`PairedRuns`, неделя 8) требует
общего строгого порядка. TREC-файлы обычно отсортированы по id как по числу
(`9`, `10`), а строковый порядок — `"10" < "9"`.

**Решение.** `iter_run(check=...)`:

- `"grouped"` (по умолчанию): повторное появление уже закончившегося запроса —
  `UngroupedInputError`. Для этого хранится множество id закончившихся запросов.
- `"sorted"`: `curr < prev` как строк — `UnsortedInputError`. Память O(1).

Нарушение контракта фатально и в non-strict режиме: пропустить «часть запроса»
нельзя, результат был бы молча неверным.

**Цена `grouped` (замер).** ~190 байт на запрос (строка id + ячейка множества).
Строки закончившихся запросов не хранятся — проверено тестом с `tracemalloc`,
который падает, если reader начинает накапливать выдачи. На 1 млн запросов это
~190 МБ; qrels на тот же миллион запросов в памяти заметно больше, так что
узким местом множество не становится. В `sorted` пиковая память одинакова
на 500, 5 000 и 50 000 запросов.

**Почему не только `sorted`.** Численно отсортированный TREC-прогон падал бы
на ровном месте, хотя для `eval` он корректен. **Почему не только `grouped`.**
Merge-join на таком входе молча пропускал бы запросы.

**Альтернативы.** Хранить хеши вместо строк — экономия небольшая (int в Python —
тоже объект), зато ложное срабатывание при коллизии. Bloom-фильтр — ложные
`UngroupedInputError` без возможности перепроверить.

## D-014. `read_qrels` вместо `iter_qrels` — принято, отступление от первоначального дизайна

**Контекст.** Метрики ищут релевантность пары (запрос, документ) случайным доступом,
поэтому разметка всё равно целиком оказывается в `dict`. Генератор `iter_qrels`
только переложил бы сборку словаря на каждого вызывающего.

**Решение.** `read_qrels(path) -> Qrels` загружает разметку в память; порядок строк
любой (разметку часто собирают конкатенацией файлов), сортировка не требуется.
Повтор пары (query_id, doc_id) — ошибка строки: в non-strict сохраняется первая
оценка. Обработка ошибок и предупреждение — как в `iter_run`.

**Ограничение.** Разметка должна помещаться в память — записать в README.

## D-015. `ErrorCollector`: только `record` и `snapshot` — принято

**Вопрос из ревью PR #3.** Нужен ли такой открытый интерфейс, да ещё
с человекочитаемым текстом, у класса, похожего на внутренний.

**Решение.** Класс публичный: это единственный канал, по которому ошибки
non-strict режима доходят до вызывающего (генератор не может вернуть сводку
сам, поэтому накопитель передаётся снаружи). Но интерфейс сужен до двух методов:
`record(error)` для reader и `snapshot() -> ErrorSummary` для всех остальных.

- `ErrorSummary` — frozen-объект в `core/result.py`: `total`, `counts`, `examples`
  (сообщения строками, а не объекты исключений — сериализуются в JSON отчёта).
- `report` получает снимок из `core`, не завися от `io` (CONTRIBUTING, раздел 4).
- Текст — `str(summary)`: им пользуется предупреждение; отчёт рендерит из полей.

**Почему не раньше.** Проверка по стеку PR показала, что `counts` и `examples`
коллектора читали только тесты — интерфейс был открыт ради проверки внутренностей.

## D-016. Parquet, Feather и таблицы в памяти через Arrow — принято

**Запрос из ревью PR #4.** Больше популярных форматов, в первую очередь parquet,
и чтение прямо из pandas/polars; тяжёлые зависимости — лениво.

**Решение.** Один путь через Apache Arrow для всего «табличного»:

- файлы parquet (`.parquet`) и Feather/Arrow IPC (`.feather`, `.arrow`);
- любой объект с Arrow C stream (`__arrow_c_stream__`): pandas ≥ 2.2,
  polars, pyarrow, DuckDB. `iter_run(df)` и `read_qrels(df)` принимают его
  вместо пути; тип источника — `Source`.

pyarrow — extras `arrow` (`pip install 'ranklens[arrow]'`), импортируется
только при чтении таких источников; без него — `MissingDependencyError`
с командой установки. Тест проверяет, что чтение csv не импортирует pyarrow.
pandas и polars не импортируются вовсе: протокол позволяет обойтись без них.

- Чтение пачками по 65 536 строк: память ограничена и для больших parquet.
  Из parquet читаются только нужные колонки.
- Номер «строки» у Arrow-источников — номер записи с 1; имя источника в
  ошибках — путь или `<DataFrame>`.
- Значения приводятся к строкам тем же правилом, что и jsonl. Новое правило
  для обоих: **целый float → целое** (`7.0` → `"7"`). pandas превращает целые id
  с пропусками в float, и без этого `7.0` не совпал бы с `"7"` в разметке (D-011).
  `NaN` и `null` в обязательном поле — «поле пустое».

**Отклонено.**

- JSON-массив целиком (`.json`) — не потоковый, а jsonl уже есть.
- zstd — в стандартной библиотеке только с Python 3.14; `.gz`, `.bz2`, `.xz`
  добавлены без зависимостей.
- Отдельные адаптеры под pandas и polars — Arrow-протокол покрывает обе
  библиотеки одним кодом и не требует их импорта.

## D-017. Протокол `Metric` без имени, реестр фабрик, синтаксис спецификаций — принято (закрывает Q-2)

**Контекст.** В плане у `Metric` был атрибут `name`, а в обосновании — «метрикой может
быть обычная функция». Это противоречие: у функции нет `name`, mypy её отвергнет.
Кроме того, у метрик бывают параметры (gain у NDCG, `rel` у AP), которые не помещаются
в сигнатуру `(ranked, judgements, k)`.

**Зачем реестр.** Это единая точка «имя → метрика» для всех, кто получает метрику
строкой: CLI, `evaluate` в библиотеке, дальше — сравнение, отчёты и сторонние метрики
через entry points (неделя 6). Новая метрика — один вызов `register`, потребители не меняются.

**Решение.**

- `Metric` — только сигнатура `__call__(ranked, judgements, k) -> float`. Обычная функция
  и экземпляр класса с `__call__` удовлетворяют ему без наследования (проверено mypy;
  функция с другой сигнатурой отвергается).
- Имя — у спецификации, а не у метрики. Реестр хранит **фабрики**: `имя -> factory(**params)`.
  Класс метрики сам является фабрикой (`registry.register("ndcg", NDCG)`), функция без
  параметров — через декоратор `@registry.metric("name")`.
- Синтаксис — как в ir_measures, привычный в IR: `ndcg`, `ndcg@10`, `ndcg(gain=exp)@10`.
  Имя без учёта регистра, параметры сортируются: `str(spec)` — канонический вид и подпись
  в отчётах. Значения: int, затем float, иначе строка.
- Ошибки: неизвестное имя — `MetricNotFoundError` с ближайшим совпадением; неразбираемая
  спецификация или неверный параметр — `MetricSpecError`.
- `Registry` — класс, а не модульный словарь: тесты создают свой реестр и не загрязняют
  глобальный. Реестр встроенных метрик живёт в `ranklens.metrics` (механизм — в `core`,
  содержимое — в `metrics`, `core` не импортирует метрики).

**Альтернативы.** Двоеточие (`ndcg@10:gain=exp`) не требует кавычек в shell, но не совпадает
с ir_measures; в CLI метрики передаются отдельными аргументами, так что кавычки нужны
только при параметрах.

## D-018. Значения метрик по умолчанию — как в trec_eval — принято (закрывает Q-4, часть Q-3)

**Контекст.** Одна и та же «NDCG@10» у trec_eval и у LTR-библиотек (LightGBM, CatBoost,
XGBoost) — разные числа: линейный gain против 2^rel − 1. Для AP@k знаменатель — R
(trec_eval) или min(k, R). Если значения по умолчанию не совпадают с опубликованными,
пользователь сравнит несравнимое.

**Решение (выбор автора).** По умолчанию — как в trec_eval, числа совпадают со статьями
и с pytrec_eval без флагов:

- `ndcg`: gain = rel, отрицательная релевантность → 0; IDCG — по **всем** размеченным
  документам запроса, обрезанным на k. `ndcg(gain=exp)` — вариант LTR-библиотек.
- `map`: релевантен документ с rel ≥ `rel` (по умолчанию 1); знаменатель — **все**
  релевантные документы R, поэтому AP@k < 1 при R > k.
- `mrr`: 1 / ранг первого релевантного в пределах k, иначе 0.
- Неразмеченный документ = нерелевантный (rel 0).
- **Q-4:** нет ни одного релевантного документа — метрика 0, как в trec_eval. Число
  таких запросов показывается в результате отдельно (неделя 5, `evaluate`). Для парных
  сравнений это почти нейтрально: у обеих систем 0, дельта 0, t-статистика не меняется.

Отдельного режима `trec_compat` не нужно — совместимость и есть умолчание. Остаётся одна
часть Q-3: trec_eval пересортировывает выдачу по score. Это вопрос чтения (`io`), а не
метрик — решается вместе с golden-тестами (неделя 6).

**Имена (уточнено по ревью PR #11).** Метрика считается **по запросу**, в отчёт идёт её
**среднее по запросам**:

| Класс | По запросу | Среднее по запросам | Имя в реестре |
|---|---|---|---|
| `NDCG` | NDCG | mean NDCG | `ndcg` |
| `AP` | average precision | MAP — mean average precision | `map` |
| `RR` | reciprocal rank | MRR — mean reciprocal rank | `mrr` |

Классы названы по тому, что считают (как в ir_measures: `AP`, `RR`), имена в реестре —
по тому, как пишут результаты (`map@10`, `mrr@10`).

## D-019. `evaluate` и коды выхода CLI — принято, отступление от плана

**`evaluate(runs, qrels, metrics)`** — один проход по потоку выдач, все метрики сразу;
спецификации разрешаются до чтения первого запроса, опечатка в имени метрики падает
сразу. Запросы:

- в прогоне и в разметке — оцениваются;
- без релевантных документов — 0 (D-018), число — `n_without_relevant`;
- в прогоне, но не в разметке — пропускаются и считаются (`n_unjudged`),
  в strict — `MissingQrelsError`; trec_eval пропускает их молча;
- в разметке, но не в прогоне — не учитываются, как в trec_eval без `-c` (`n_not_retrieved`).

`MetricResult.per_query` — `MappingProxyType`: результат читают статистика и отчёты,
изменить его не может ни один из них. Среднее — `math.fsum`, для пустого результата — NaN
(в JSON — `null`).

**Коды выхода.** В плане: 0 — успех, 1 — ошибка выполнения, 2 — ошибка данных.
Но код 2 по соглашению занимает argparse (неверные аргументы), и `ranklens --bad-flag`
неотличим от битых данных. Итог:

| Код | Когда |
|---|---|
| 0 | успех (пропущенные в non-strict строки — предупреждение в stderr) |
| 1 | ошибка конфигурации или выполнения: неизвестная метрика, нет файла |
| 2 | неверные аргументы (argparse) |
| 3 | ошибка данных: битая строка в strict, нарушение порядка, нет разметки в strict |

## D-020. ERR и RBP: шкала релевантности и нормировка — принято (закрывает Q-5)

**ERR** (Chapelle et al., 2009): R = (2^rel − 1) / 2^max_rel — вероятность, что документ
удовлетворит и пользователь остановится. `max_rel` — верх **шкалы**, а не максимум
по запросу: иначе запрос с оценками 0–1 и запрос с 0–3 были бы несравнимы.
По умолчанию 4, как в TREC gdeval; для шкалы 0–3 — `err(max_rel=3)`.

**RBP** (Moffat & Zobel, 2008): (1 − p) · Σ rel_r · p^(r−1), rel ∈ [0, 1].
По умолчанию бинарная релевантность (rel ≥ 1) и p = 0.8; градуированная —
`rbp(max_rel=3)`: min(rel, max_rel) / max_rel. Нормировка на шкалу держит RBP в [0, 1] (Q-5).
RBP@k — нижняя граница: хвост после k не учитывается, остаток p^k не сообщается.

**Оценка выше шкалы** считается равной `max_rel`: это поведение описано в docstring
и проверено тестом, а не тихое округление. Неположительная — 0.

**Идеальный порядок ≠ 1** для обеих метрик: даже идеальный документ оставляет шанс
продолжить просмотр, поэтому инвариант «идеал = 1» к ним не применяется.

Валидация параметров вынесена в `metrics/base.py` (`positive`, `probability`): параметры
приходят из строки спецификации, так что проверяются в runtime, какой бы ни была аннотация.

## D-021. RBO — функция сравнения двух прогонов, не метрика — принято

RBO (Webber, Moffat & Zobel, 2010) сравнивает **два порядка** без разметки: насколько
новая модель переставила выдачу. Протокол `Metric` — это «выдача против разметки»,
поэтому RBO не регистрируется в реестре, а экспортируется функцией `ranklens.metrics.rbo`.
Её потребитель — сравнение прогонов (`PairedRuns`, неделя 8) и `rank_flow`.

- Формула — экстраполированный RBO_ext для одинаковой глубины (eq. 32); оба списка
  сравниваются на глубине более короткого. Неравные длины (eq. 30) — вне скоупа,
  записать в «Ограничения».
- Перекрытие префиксов считается инкрементально по двум множествам: O(k), а не O(k²).
- Проверено: вручную (0.875 для xyz/xzy, p = 0.5); свойства — идентичные = 1,
  непересекающиеся = 0, симметрия, [0, 1], перестановка вверху весит больше, чем внизу.

## D-022. Порядок по score как в trec_eval и golden-тесты — принято (закрывает Q-3)

**Проверено экспериментом с pytrec_eval:** trec_eval игнорирует порядок строк и колонку
rank, сортирует выдачу по score по убыванию, при равенстве — по docno **по убыванию
как строки** (`"d9"` раньше `"d10"`).

**Решение.**

- `iter_run(order="score")` сортирует так же: `sorted(..., key=(score, doc_id), reverse=True)`.
- **Для TREC-файлов это порядок по умолчанию**, для остальных форматов — порядок файла.
  Логика та же, что в D-018: числа по TREC-прогону совпадают с trec_eval без флагов.
  Явный `order=` перекрывает умолчание.

**Golden-тесты.** `scripts/make_golden.py` один раз генерирует эталон через
pytrec-eval-terrier (сборка pytrec_eval с колёсами) и коммитит его в `tests/data/golden/`;
в CI pytrec_eval не нужен. Данные синтетические, с фиксированным seed: 40 запросов,
равные score, отрицательная и градуированная релевантность, неразмеченные документы,
запросы без релевантных, запросы только в прогоне и только в разметке, id `"9"`/`"10"`.
Публичные qrels (TREC DL) не взяты: у них своя лицензия, а новых случаев они не добавили бы.

Результат: `ndcg`, `ndcg@5/10/100`, `map`, `map@10/100`, `mrr` совпадают с trec_eval
по каждому запросу до 1e-9. Чувствительность проверена мутацией: чтение в порядке файла
роняет все 8 сверок, `gain=exp` — сверку NDCG.

ERR и RBP в trec_eval нет, для них — ручные значения и инварианты (D-020).

## D-023. Векторизация: одна матрица на пачку запросов — принято (закрывает Q-11)

**Где время.** Поиск релевантности каждого документа в словаре остаётся циклом Python
при любом подходе. Выигрыш — в том, что после него: матрица релевантностей строится
**один раз на пачку** и её используют все метрики, а арифметика (дисконты, накопленные
суммы, произведения) идёт в numpy.

**Решение.**

- `Batch(relevance, ideal)`: матрицы пачки, дополненные нулями (0 = нерелевантен,
  поэтому дополнение не меняет ни одну метрику).
- Протокол `BatchMetric` (в `metrics`, потому что с numpy): метод `batch(batch, k)`.
  Его реализуют все встроенные метрики; сторонние без `batch` по-прежнему считаются
  по запросу, в том же проходе.
- `evaluate(batch_size=1024)`: в памяти одна пачка, а не весь прогон — потоковость сохранена.
- Эквивалентность: Hypothesis сравнивает `batch` с поштучным расчётом до 1e-12 для всех
  встроенных метрик и параметров; результат `evaluate` не зависит от размера пачки;
  golden-сверка с trec_eval теперь идёт через векторный путь.

**Замер** (2 000 запросов × 100 документов, 6 метрик, Python 3.11, M-серия):
по одному запросу — 153 мс, пачками по 1024 — 20 мс, **в 7.5 раза быстрее**.

**Бенчмарк в CI (Q-11)** — задача `bench`, `continue-on-error`, не входит в обязательные
проверки; результаты — артефакт `benchmark.json`. Порог «регрессия > 20 %» на общих
раннерах GitHub давал бы ложные падения.

## D-024. Плагины метрик через entry points — принято

**Решение.** Встроенный реестр создаётся с группой `ranklens.metrics`; установленные
пакеты публикуют в ней **фабрики** метрик. Механизм — в `core` (`importlib.metadata`,
только stdlib), `core` не знает ни одного плагина.

- **Лениво:** плагины загружаются при первом `names()`/`resolve()`, а не при
  `import ranklens` — импорт библиотеки не исполняет чужой код и не замедляется.
- **Отказоустойчиво:** плагин, который не импортируется, падает при загрузке или
  занимает существующее имя, пропускается с `PluginWarning` (имя, путь, пакет).
  Это единственное место с `except Exception`: код плагина произвольный, а один сломанный
  пакет не должен ломать все команды. Встроенные имена плагином не перекрываются —
  подмена `ndcg` чужой реализацией была бы тихой ошибкой в результатах.
- `ranklens metrics` — список доступных метрик, включая плагины.

**Проверено:** юнит-тесты с подменённым `entry_points` (ленивость, однократность,
четыре вида отказа) и сквозной тест: во временной папке создаётся пакет с `dist-info`
и `entry_points.txt`, `python -m ranklens eval --metrics 'hits(rel=2)@10'` в отдельном
процессе использует его метрику. How-to — `docs/howto/custom-metric.md`.

## D-025. Paired bootstrap: ресемплинг запросов, перцентильный интервал, чанки — принято

**Единица наблюдения — запрос, а не строка.** Позиции внутри одной выдачи зависимы:
ресемплинг строк «размножил» бы независимые наблюдения и дал заметно более узкий
интервал, чем есть на самом деле. Ресемплим запросы с возвращением, выдачи не трогаем.

- `paired_deltas` берёт **пересечение** запросов двух прогонов: парный тест требует пар.
  Запросы, измеренные только в одном прогоне, отбрасываются (их число попадёт
  в `ComparisonResult`).
- Нет ни одного общего запроса — `InsufficientSampleError`: сравнивать нечего.
  Меньше `MIN_QUERIES = 20` — **предупреждение** `SmallSampleWarning`, а не ошибка
  (уточнено по ревью PR #18): исключительной ситуации нет, число считается, просто
  интервал широкий и p-value неустойчив. Порог настраивается (`min_queries`).
- Интервал — **перцентильный** (квантили ресемплированных средних). Он недопокрывает
  на малых и скошенных выборках; проверка покрытия это и показывает как границу применимости.
- **Чанки.** Матрица индексов `(n_resamples, n_queries)` при 100k запросов и 10k ресемплов
  заняла бы ~8 ГБ, поэтому ресемплы берутся кусками по ~64 МБ. Проверено: numpy выдаёт
  ту же последовательность при любом разбиении, поэтому результат от размера чанка
  не зависит (тест сравнивает три разных чанка).
- `seed` и `n_resamples` лежат в результате: число в отчёте должно воспроизводиться.

**Валидация (уровень 4).** 1000 симуляций с известной разницей: 95%-й интервал накрывает
истину в 95.3% случаев, допуск — три биномиальных стандартных ошибки (0.929…0.971).
Прогон занимает около секунды, поэтому тест идёт в обычном наборе, без пометки «медленный».

## D-026. p-value из перестановочного теста, интервал из bootstrap — принято (закрывает Q-6, Q-7)

**Почему две процедуры.** Bootstrap естественно даёт **интервал**, а не p-value;
перестановочный тест естественно даёт **p-value**, а не интервал. Поэтому
`compare` считает обе и кладёт в `ComparisonResult` и то, и другое; в докстринге
результата написано, что откуда взялось, чтобы это не выяснялось по коду (Q-6).

**Перестановочный тест (Q-7).** Двусторонний, со сменой знака разницы по каждому
запросу: под нулевой гипотезой знак произволен. p-value = `(b + 1) / (m + 1)` —
наблюдаемое распределение входит в референсный набор, поэтому ноль не выдаётся
никогда; при 10 000 перестановок минимум — около 1e-4. Сравнение «не менее
экстремально» — с допуском 1e-12: иначе равенство теряется на числах с плавающей точкой.

**Проверка равномерности — долей отвержений, а не KS-тестом.** p-value дискретен
(шаг 1/(m+1)), и KS отверг бы равномерность на совершенно нормальных данных.
Тест: 1000 симуляций без эффекта, доля `p ≤ α` для α = 0.05, 0.1, 0.2 внутри трёх
биномиальных стандартных ошибок. Плюс проверка мощности: эффект в половину
стандартного отклонения на 200 запросах ловится в 45+ случаях из 50.

**Независимые потоки случайности.** Из одного пользовательского `seed` через
`SeedSequence.generate_state(2)` получаются два независимых зерна — bootstrap и
перестановки не должны делить одну последовательность. В результате хранится
исходный seed: воспроизводится всё сравнение целиком.

**Средние считаются по парным запросам**, иначе `mean_b - mean_a` не совпало бы
с `delta`, а это первое, что проверит читатель отчёта. Число непарных запросов
с каждой стороны — в результате (`n_only_a`, `n_only_b`).

**Общий модуль `stats/chunking.py`** для разбиения матрицы ресемплов: им пользуются
и bootstrap, и перестановки, и оба теста проверяют независимость результата от размера чанка.

## D-027. Сайт документации: mkdocs-material + mkdocstrings, примеры исполняются — принято

**Стек.** mkdocs-material (тема, поиск, тёмная тема), mkdocstrings (справочник API
прямо из docstring, без дублирования), markdown-exec (исполняемые примеры).
Sphinx с темой pydata — стек pandas — сильнее на огромных API и перекрёстных ссылках,
но настраивается дольше и на нашем размере выигрыша не даёт.

**Примеры исполняются при сборке.** Блок кода в документации запускается, его настоящий
вывод попадает на страницу, а сборка идёт с `--strict`. Устаревший пример роняет CI,

качества сайта, а не тема оформления.

**Раньше плана.** По плану сайт был на 13-й неделе, но там же заморозка фич, релиз
и подготовка к защите. Документация, написанная в последнюю неделю по готовому коду,
выходит формальной, поэтому каркас поднят сейчас, а страницы дописываются по неделям,
пока материал свежий.

**Sphinx-роли в docstring** (`:class:`X``) переведены в обычные обратные кавычки:
mkdocstrings их не превращает в ссылки и показал бы как текст.

**Курсовые артефакты** (`decisions.md`, `llm-log.md`) исключены из сайта через

**Данные для примеров** лежат в `docs/examples/` и совпадают с `tests/data/toy.*` —
это проверяется тестом, чтобы копии не разошлись.

**Публикация.** Задача `docs-build` собирает сайт на каждом PR, `docs-deploy`
публикует его на GitHub Pages только с `main`.

## D-028. BH-коррекция и MDE — принято

**Benjamini-Hochberg.** При сравнении по 40 сегментам на α = 0.05 два «значимых»
сегмента появляются сами собой. BH контролирует **FDR** — ожидаемую долю ошибок
среди объявленных находками, а не вероятность хотя бы одной ошибки (это было бы FWER
и Bonferroni, который на десятках сегментов почти всё занулит). В отчёт идёт q-value.

- `benjamini_hochberg(p_values)` возвращает q-values в порядке входа; сверено
  с опубликованным примером из статьи
  [Benjamini & Hochberg (1995)](https://doi.org/10.1111/j.2517-6161.1995.tb02031.x).
- `adjust(results)` заполняет `q_value` в `ComparisonResult`; `significant` после этого
  смотрит на q-value, а не на p-value.
- Валидация: при 200 «семьях» по 10 сравнений без эффекта хотя бы одна находка
  появляется не чаще, чем в α случаев.

**MDE.** MDE = (z(1−α/2) + z(power)) · sd / √n — нормальное приближение для среднего
поразапросных разниц. Квантили берутся из `statistics.NormalDist` стандартной библиотеки,
scipy не нужен (он потянул бы тяжёлую обязательную зависимость ради двух чисел).

- Обратная функция `required_queries(delta, sd)` отвечает на вопрос «сколько запросов
  нужно»: при sd = 0.1 прирост +0.02 требует ~200 запросов, +0.01 — ~800, +0.005 — ~3100.
- Валидация: при истинном эффекте, равном MDE(power = 0.8), перестановочный тест
  отвергает H0 примерно в 80% симуляций — приближение согласуется с самим тестом.
- Смысл для пользователя: маленький эффект не «отсутствует», он **ниже разрешающей
  способности** этой выборки запросов. Это же сообщение даёт `InsufficientSampleError`
  и `SmallSampleWarning`.

## D-029. `PairedRuns` — свой итератор merge-join — принято

**Зачем не `zip`.** У двух прогонов разные и лишь частично пересекающиеся множества
запросов: `zip` спарил бы несвязанные выдачи, как только один прогон пропустит запрос,
и сделал бы это молча. Merge-join идёт по двум отсортированным потокам с буфером
в одну выдачу на сторону, поэтому два больших прогона по-прежнему читаются потоково.

- Запросы, встретившиеся только слева или только справа, **считаются** (`only_left`,
  `only_right`), а не пропускаются незаметно.
- Несортированный вход — `UnsortedInputError`: на нём merge-join молча терял бы запросы.
  Для потоков, склеенных в памяти, номера строки нет, поэтому `line_no` стал
  необязательным, а в сообщении указывается сторона (`left run` / `right run`).
- Контекстный менеджер закрывает оба потока — полезно, когда цикл прерывают досрочно.

**Кому нужен.** Всему, что требует обе выдачи одновременно: RBO (насколько переставился
порядок), `rank_flow` в визуализации, pairwise-объяснения. Для `compare` он не нужен:
там метрики считаются по каждому прогону отдельно.

## D-030. Сравнение по сегментам — принято

**Где берутся сегменты.** `evaluate` сохраняет значения сегментных колонок оценённых
запросов в `Evaluation.segments`; срез делается по готовой оценке, прогон второй раз
не читается. Запросы без разметки в `segments` не попадают — их нет и в метриках.

**`compare_segments`** — одна строка на сегмент: средние, дельта, интервал, p-value,
q-value. Коррекция BH идёт по всем сегментам одной метрики.

- Сегменты не пересекаются по запросам, поэтому их сравнения независимы — это ровно
  условие, при котором BH контролирует FDR на уровне α.
- Сегменты меньше `min_queries` показываются с пустой статистикой и в коррекцию
  не входят. Отбор идёт по размеру, а не по результату, поэтому FDR не смещает.
- **У каждого сегмента свой поток случайности** (`SeedSequence(seed)`, сегменты
  в отсортированном порядке). С одним общим seed сегменты одного размера получали
  одинаковые ресемплы: ошибки Монте-Карло коррелируют, p-values перестают быть
  независимыми. На симуляции с 50 перестановками корреляция p-values под H₀ — 0.02
  против 0.004 при независимых потоках: мало, но условие BH нарушалось без нужды.
- Интервалы — по сегменту, без поправки. Интервал может не содержать ноль при
  q-value ≥ α; решает q-value. Скорректированные интервалы (FCR, Benjamini–Yekutieli
  2005) — возможное развитие.
- `significant` сравнивает строго (`q < α`), как и p-value до коррекции; у BH в статье
  `≤`, разница только на границе.
