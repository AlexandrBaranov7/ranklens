Этот документ — договор, которому следуют все, кто пишет код в проекте,
включая авторов проекта и ассистентов. Правило, которое нельзя соблюсти,
меняется отдельным PR с обоснованием, а не нарушается молча.

## 1. Окружение

Нужны Python 3.11 и [Poetry](https://python-poetry.org/) >= 2.4
(например, `pipx install poetry`).

```bash
poetry install               # .venv в корне проекта, пакет + группа dev
poetry run pre-commit install
```

Проверки, которые гоняет CI, запускаются локально так:

```bash
poetry check --lock
poetry run ruff check . && poetry run ruff format --check .
poetry run mypy
poetry run pytest --cov
```

Разрабатываем на минимальной поддерживаемой версии Python (3.11, файл
`.python-version`): так синтаксис из более новых версий ловится сразу, а не в CI.

**Зависимости.**

- Runtime-зависимости и extras — в `[project]`, dev-инструменты — в
  `[dependency-groups]` (PEP 735).
- Добавление: `poetry add <pkg>` / `poetry add --group dev <pkg>`.
- `poetry.lock` коммитится и меняется только вместе с `pyproject.toml`
  (CI проверяет `poetry check --lock`). Обновление версий — отдельным PR
  (`poetry update`), а не попутно.
- Lock нужен для воспроизводимой разработки и CI; пользователи библиотеки
  его не видят и ставят пакет обычным `pip install`.

## 2. Процесс: ветки, коммиты, PR

**Ветки.** `main` защищена, прямые коммиты в неё запрещены.
Имя ветки — `<тип>/<кратко>`: `feat/ndcg`, `fix/unsorted-input`,
`docs/math-metrics`, `test/bootstrap-coverage`, `refactor/registry`, `chore/ci-cache`.

**Один PR — одна связная единица работы.** Не «неделя 7», а «paired bootstrap».
Если описание PR требует слова «а также» — скорее всего, это два PR.
Ориентир по размеру — до ~400 строк изменений без учёта тестовых данных.

**Коммиты.**

- Заголовок на английском, в повелительном наклонении, до 72 символов:
  `Add paired bootstrap`, `Fix NDCG for empty qrels`.
- Тело — по необходимости, 1–3 строки: зачем, а не что.
- Никаких email-адресов в сообщениях, никаких трейлеров `Co-Authored-By`.
- Коммит делается по мере работы, а не одним куском перед дедлайном.
  История разработки — часть результата.
- Автор коммитов — GitHub noreply-адрес, а не рабочая почта.

**Pull request.**

- Описание по шаблону: что, почему так, что протестировано.
- Мерж только при зелёном CI.
- Стратегия мержа — **Rebase and merge**: история линейная, отдельные
  коммиты с их датами сохраняются.
- `CHANGELOG.md` (секция `Unreleased`) обновляется в том же PR.
- Если в работе участвовал ассистент — запись в `docs/llm-log.md` в том же PR.

## 3. Границы проекта

Что ranklens **не делает** и делать не будет без отдельного решения
в `docs/decisions.md`:

- не обучает модели и не подбирает гиперпараметры — только оценивает;
- не является онлайн-сервисом: никакой сети во время работы, никакой телеметрии;
- не распределённый: один процесс, потоковая обработка файлов;
- не читает неотсортированный вход молча — либо явная ошибка, либо явный `--sort`;
- не десериализует недоверенные данные исполняемыми форматами (pickle)
  без явного флага пользователя.

Ограничения по зависимостям:

- обязательные runtime-зависимости — только `numpy` и `pandas`;
- новая обязательная зависимость — только через запись в `docs/decisions.md`;
- всё тяжёлое (plotly, catboost, lightgbm, xgboost, scikit-learn, pyarrow, scipy) —
  в extras и импортируется лениво.

## 4. Архитектурные границы слоёв

Разрешённые зависимости между подпакетами. Правила проверяются автоматически
тестом `tests/test_architecture.py`: нарушение — красный CI, а не замечание на ревью.

| Подпакет | Может импортировать | Сторонние библиотеки |
|---|---|---|
| `core` | — | только stdlib |
| `io` | `core` | stdlib; `pyarrow` лениво |
| `metrics` | `core` | `numpy` |
| `stats` | `core` | `numpy` |
| `offpolicy` | `core`, `metrics`, `stats` | `numpy` |
| `explain` | `core`, `metrics` | `numpy`; модели и `scipy` лениво |
| `aggregate` | `core`, `metrics`, `stats` | `numpy`, `pandas` |
| `viz` | `core` | `plotly` лениво |
| `report` | `core`, `viz` | `pandas` |
| `cli` | всё | stdlib |

Смысл правил:

1. **`core` — словарь проекта.** Типы, протоколы, исключения, результаты.
   Он не должен тащить numpy: протоколы, которым нужен `ndarray`, живут в своём
   слое (`ScorerAdapter` — в `explain`).
2. **`metrics` не знает про файлы и отчёты.** Метрика — чистая функция
   от выдачи и разметки.
3. **`viz` не считает математику.** Принимает готовый `*Result` и рисует.
   Нужна новая величина — она считается в `metrics`/`stats`.
4. **`io` не знает про метрики.** Отдаёт `RankedList`, дальше не его дело.
5. **pandas — только в `aggregate` и `report`.** Горячие циклы на Python/numpy,
   иначе теряется потоковость.
6. **Опциональные зависимости изолированы.** Импорт — внутри функции
   или адаптера, при отсутствии пакета — ошибка с командой установки.

## 5. Правила кода

**Типизация.**

- `mypy --strict` для пакета и тестов, без исключений.
- `Any` в публичном API запрещён. `# type: ignore` — только с кодом ошибки
  (`# type: ignore[attr-defined]`) и только если иначе нельзя.
- Точки расширения — `typing.Protocol`, а не ABC: реализация не обязана
  наследоваться от наших классов.

**Данные.**

- Объекты-значения — `@dataclass(frozen=True, slots=True)`.
- Внутри frozen-объекта — только неизменяемые коллекции (`tuple`, `frozenset`).
  `frozen=True` защищает только атрибуты, но не список внутри атрибута.
- Изменяемые коллекции (`list`, `dict`, `set`) — для накопления внутри функций
  и для индексов, а не для полей результата.
- Позиции в выдаче хранятся **с нуля** (`position`). В формулах ранг — `position + 1`.
  Имена переменных это отражают: `position` против `rank`.
- `QueryId`/`DocId` — строки. Порядок сортировки входных файлов — лексикографический
  по строке (`"10" < "9"`).

**Ошибки.**

- Публичный код бросает только наследников `RankLensError`
  (исключение — `TypeError`/`ValueError` на явно неверные аргументы функции,
  то есть на ошибку программиста, а не данных).
- Никаких `raise Exception(...)`, `except Exception: pass` и голых `except:`.
- Сообщение об ошибке отвечает на три вопроса: что случилось, где (файл, строка,
  query_id), что делать.
- Структурированные данные ошибки — в атрибутах, а не только в тексте.
- Исключения переживают `pickle` (понадобится при multiprocessing):
  аргументы конструктора передаются в `super().__init__`.

**Побочные эффекты.**

- Библиотека не пишет в stdout (`print` запрещён линтером вне `cli.py`).
- Диагностика — `logging.getLogger(__name__)`, без настройки хендлеров.
  Предупреждения пользователю — `warnings.warn` с конкретной категорией.
- Файлы-результаты пишутся атомарно (через `AtomicReport`), полуфайлов не бывает.

**Случайность и воспроизводимость.**

- Любая функция со случайностью принимает `seed: int` или `numpy.random.Generator`.
- Глобальное состояние `np.random.*` и `random.*` не используется.
- Seed попадает в объект результата и в отчёт.
- Одинаковый вход и seed → побайтово одинаковый JSON-вывод.

**Стиль.**

- Форматирование и импорты — `ruff format` / `ruff check`, без ручных споров.
- Комментарии короткие и объясняют «почему», а не «что».
- Докстринг обязателен для публичных функций и классов: одна строка сути;
  для метрик и оценщиков — формула или ссылка на `docs/math/`.
- Публичный API — то, что перечислено в `__all__`. Остальное — с `_` в имени
  или без гарантий совместимости.

## 6. Тесты

- Код без тестов не мержится. Тесты пишутся в том же PR, что и код.
- Покрытие не ниже 85% (гейт в CI), но покрытие — нижняя граница, а не цель.
- Уровни тестов:
  1. точные значения на примерах, посчитанных вручную;
  2. инварианты через Hypothesis;
  3. сверка с эталонными реализациями на закоммиченных данных;
  4. статистическая валидация на симуляциях.
- Статистические и долгие тесты помечаются `@pytest.mark.slow`.
- Тесты не ходят в сеть, пишут только в `tmp_path`, используют фиксированный seed.
- Сравнение float — через `pytest.approx` или `math.isclose` с явным допуском.
- Инвариант, заявленный в тесте, сначала проверяется на бумаге.
  Пример ловушки: NDCG@k **не** монотонна по k (растёт IDCG), монотонна только DCG@k.
- Предупреждения в тестах считаются ошибками (`filterwarnings = error`).
  Ожидаемое предупреждение проверяется через `pytest.warns`.

## 7. Документация и решения

- Нетривиальное решение (структура данных, формула по умолчанию, новая зависимость) —
  запись в [`docs/decisions.md`](docs/decisions.md): контекст, решение,
  отвергнутые альтернативы. Это временный журнал (раздел 11): решения, важные
  пользователям, к релизу переносятся в постоянную документацию.
- Формулы метрик и оценщиков — в `docs/math/` со ссылкой на источник
  и с оговорками о граничных случаях (пустая разметка, IDCG = 0 и т. п.).
- Язык: код, идентификаторы, докстринги и коммиты — английский;
  README, CONTRIBUTING и `docs/` — русский.

## 8. Работа с LLM-ассистентом

Ассистент разрешён и используется. Ответственность за код — на авторе PR.

- **Главное правило:** каждое архитектурное решение и каждая нетривиальная функция
  должны быть выводимы заново без ассистента. Если кусок кода нельзя объяснить —
  PR не готов, даже если тесты зелёные.
- В `docs/llm-log.md` (временный, раздел 11) на каждый значимый PR — короткая
  запись: что предложил ассистент, что не устроило, что переписано вручную и почему.
  Запись делается сразу, а не в конце разработки.
- Перед мержем автор отвечает себе на три вопроса:
  1. Понимаю ли я, почему здесь такая структура данных?
  2. Смогу ли я объяснить, что сломается, если поменять вот эту строку?
  3. Есть ли здесь конструкция, которую я бы сам не написал и не понимаю?

  «Да» на третий вопрос — стоп-сигнал: разобраться или переписать проще.
- Ассистент не пушит, не мержит и не создаёт релизы без явного подтверждения автора.

## 9. Definition of Done для PR

- [ ] CI зелёный: ruff, mypy strict, тесты на всей матрице, установка wheel.
- [ ] Тесты на новое поведение, включая граничные случаи и ошибки.
- [ ] Публичное API типизировано и задокументировано.
- [ ] `CHANGELOG.md` обновлён.
- [ ] Нетривиальные решения записаны в `docs/decisions.md`.
- [ ] Запись в `docs/llm-log.md`, если участвовал ассистент.
- [ ] Автор может объяснить каждую строку (раздел 8).

## 10. Релизы

- Версионирование — [SemVer](https://semver.org/lang/ru/). До `1.0.0` минорная
  версия может ломать API, но каждое такое изменение отмечено в CHANGELOG.
- CHANGELOG — в формате [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/).
- Версия задаётся в одном месте — `version` в `pyproject.toml` (`poetry version patch|minor`);
  `ranklens.__version__` читает её из метаданных установленного пакета.
- Релиз — тег `vX.Y.Z` на `main`, сначала публикация в TestPyPI.
- Перед первым релизом на PyPI репозиторий чистится от временных артефактов (раздел 11).
  Релизы на TestPyPI до этого — репетиции.

## 11. Временные артефакты разработки

Проект разрабатывается как курсовая работа по плану, который ведётся вне
репозитория. Часть файлов нужна только на время разработки и защиты:

| Артефакт | Зачем сейчас | Что с ним перед релизом |
|---|---|---|
| `docs/decisions.md` | журнал решений и открытых вопросов | значимое — в `docs/design.md`, файл удаляется |
| `docs/llm-log.md` | требование курса: лог работы с ассистентом | удаляется |
| упоминания в разделах 7–10, этот раздел, пункт в шаблоне PR | процесс разработки | удаляются |

Чистка — отдельный PR после защиты курсовой. Коммит перед ней помечается
тегом `course-artifacts`, чтобы артефакты оставались доступны по постоянной ссылке.
В пакет (wheel, sdist) эти файлы не попадают и сейчас.

Временный артефакт не должен становиться зависимостью постоянного: код, тесты
и README на них не ссылаются.
